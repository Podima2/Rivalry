# Rivalry implementation handoff

Updated 2026-09-27. Read `InitialPlan.md` for the product decisions and acceptance scenarios, then `mobile/CLAUDE.md` and `mobile/AGENTS.md` before changing the Expo app. The target is a two-phone Android/iPhone demo, not an app store release. Keep crypto out of the user interface and label World Sandbox checks as simulated.

## Current state

- Expo SDK 57 / React Native 0.86 app in `mobile/`. Privy email login and embedded Ethereum wallet creation are configured in `src/app/_layout.tsx`. Handle selection uses `runner-profile` when Supabase public values are configured and falls back to phone storage otherwise. Unique handles exist in Postgres, but wallet address capture and Sepolia ENS subname registration/resolution are **not implemented**.
- Friend flow: four-digit, ten-minute invite code and `rivalry:///?invite=CODE` link; atomic join for two runners; each selects a GPS-derived, movable start and reviews a route; both accept routes and confirm readiness; one server-scheduled 15-second countdown. UI is mainly `mobile/src/app/index.tsx` and `src/components/RoutePicker.tsx`.
- Stranger flow: server-side queue by distance, match, route acceptance and readiness, race-specific World verification, countdown. Waiting runners remain queued until leaving or changing distance. A runner who declines a pre-start match causes the other runner to be requeued. Sandbox currently blocks **10 km stranger queueing** because its Official ID credential cannot be issued in this setup; the UI says demo only.
- Route preview is served by `supabase/functions/route-preview/index.ts` using server-side ORS foot-walking. It requests a loop, retries once for distance, then tries measured out-and-back. A 10 km route repeats a 5 km route. Routes must be within 5% of the preset and of each other. The API stores exact starts, coordinates, elevation profile and gain privately; opponent status exposes only distance/gain/acceptance.
- Active race UI is `src/components/RaceLive.tsx`. It currently watches **foreground** GPS, polls progress every four seconds, warns for weak/lost GPS or off-route fixes, shows friend location, hides stranger location, and supports DNF. `race-progress` projects fixes onto the private route, applies movement gates, and finalizes when both runners finish or DNF. Finalization writes summary rows and deletes `race_gps_points` in one SQL transaction. No physical two-device end-to-end result is established by this handoff.
- `world-verification` starts server-signed, race-scoped IDKit attempts and verifies returned results with World. The mobile UI runs IDKit inside a hidden WebView and opens the World app through its connector URI. It stores outcomes, not raw proofs. The standalone Sandbox preview does **not** verify a race. Real matched-race checks are only available in `verification` state.
- Current working tree contains extensive **uncommitted and untracked implementation** beyond commit `625c946`. Preserve it; inspect `git status` before editing or committing. `mobile/.env` exists and contains local values: never print or commit it.

## Codebase nuances and constraints

- Authentication is **Privy, not Supabase Auth**. `supabase/config.toml` disables platform JWT verification for these functions; every function instead verifies the Privy bearer token in `_shared/auth.ts` and derives `privy_user_id` from it. Database tables have RLS enabled and direct client grants revoked. Never accept a profile ID from the request body or put service-role, ORS, World RP signing, or ENS keys in the mobile app.
- The migrations repeatedly replace the same SQL functions. Read the **latest definition** (`20260926110000_shared_race_progress.sql`, `20260926120000_stranger_queue_stability.sql`) before changing behavior; append a new migration rather than modifying a migration already deployed to a shared project.
- Polling advances a scheduled countdown to `active` in the race status functions; the 15-second start is shared via `scheduled_start_at`, not a client timer. The mobile clock adjusts to server time. The home screen owns most race restoration and screen selection state.
- Route preview stores `[longitude, latitude, elevation]`; React Native maps need `{ latitude, longitude }`. The 10 km shape repeats coordinates and can contain overlaps. A GPS fix is sent at most every 3.5 seconds; `race-progress` rejects accuracy over 50 m and caps projected travel based on elapsed time. Off-route points are recorded without advancing progress.
- Friend status exposes only route metrics; `race-progress` exposes latest friend location only after activation. Stranger progress snapshots filter the opponent's GPS point and never return their route coordinates. Preserve these response boundaries when adding features.
- The World WebView loads `@worldcoin/idkit-core@4.3.0` from jsDelivr, while server functions use `@worldcoin/idkit-core` imports. This is a runtime/network dependency worth checking on both phones. A failed/rejected race proof calls `leave_stranger_race`; a user closing the World flow without submitting a result currently needs explicit verification in the two-phone test.
- Mobile native compatibility has custom setup: `entrypoint.js` installs encoding/random/ethers/quick-crypto shims before Expo Router; `metro.config.js` overrides Privy's entry and handles WASM; `babel.config.js` enables `import.meta`; `postinstall` patches **expo-modules-jsi 57.1.1** and intentionally fails if that version changes. Review these before upgrading packages. Use `npx expo install` for SDK-compatible dependencies.
- This machine currently reports **Xcode 26.2**; `InitialPlan.md` calls for 26.4+ before the iPhone SDK 57 local build. Android map setup also needs the development signing fingerprint restriction. Native libraries already added require development builds, not Expo Go.

## Setup and verification commands

From `mobile/`: `npm ci`, `npm run typecheck`, `npm run lint`, `npx expo-doctor`, then `npm run android` / `npm run ios` when device prerequisites are ready. At handoff, `npm run typecheck` and `npm run lint` both pass. No migration deployment, Edge Function deployment, device build, or end-to-end race was verified during this handoff inspection.

For Supabase, follow `supabase/README.md`: `npx supabase link --project-ref ...`, `npx supabase db push`, set Privy/ORS/World/server secrets, then deploy `runner-profile`, `friend-races`, `stranger-races`, `route-preview`, `world-verification`, and `race-progress`. Mobile public values belong in ignored `mobile/.env`; server secrets belong only in Supabase Function Secrets. Check actual remote migration and function status before treating local files as deployed.

## Completion bar

Two separate email accounts on physical Android and iPhone can complete a friend race and a Sandbox stranger race at 1/3/5 km; both routes are reviewed and accepted; the shared start, locked-screen tracking, friend-only location, stranger-only progress, valid result/DNF, and deletion of precise points are observed. Each account has a unique handle whose Sepolia ENS subname resolves to its embedded wallet. The 10 km stranger tier either passes real supported Official ID verification or remains explicitly unavailable in Sandbox. All claims should be backed by device and database observations, not just UI copy.
